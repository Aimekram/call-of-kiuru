# Call of Kiuru — Build Plan

A European phenology dashboard: for any tracked location, show how many days earlier/later
spring is arriving this year vs. the 1991–2020 baseline, modeled from open climate data.
Personalized, shareable, honest about its own uncertainty.

---

## 1. Infra & Setup (detailed)

**Repo:** one monorepo, not two.

```
/pipeline    → Python: CDS pull, SI-x model, writes to DB, generates static pages
/site        → static HTML/CSS/vanilla TS output (served by Cloudflare Pages)
/.github/workflows/daily.yml → the scheduled job tying the two together
/docs/validation.md → the running validation log (see §3)
```

**Repo visibility:** public. Two independent reasons converge on the same answer —
GitHub Actions minutes are unconditionally free on public repos (private repos get
2,000 free min/month, which would still be plenty, but why manage a limit you don't
need to), and this project's whole premise is open, EU-native data — an open repo is
consistent with that, not just cheaper.

**Accounts to create before writing code:**
- Copernicus CDS account (free) at cds.climate.copernicus.eu → generate a personal
  API token → this becomes a GitHub Actions **encrypted secret**, never committed to
  the repo (not even in a gitignored `.cdsapirc` — use the secret directly in CI).
- Manually accept the dataset-specific Terms of Use on the CDS website for
  `derived-era5-single-levels-daily-statistics` — this is a one-time click the API
  cannot do for you, and skipping it produces a confusing failure later.
- Supabase project, **Frankfurt (EU) region** — free tier (500MB DB, 50K MAU) is
  far more than this needs at launch. Copy the DB connection string into a second
  GitHub Actions secret.
- Cloudflare account for Pages hosting (free tier, unlimited bandwidth — chosen over
  Netlify's 100GB cap specifically because a viral share spike is the goal, not an
  edge case to avoid).
- Ko-fi account for the tip button (0% fee on the free plan, vs. Buy Me a Coffee's
  flat 5% — purely a numbers call, not a brand preference).

**Stack decisions, and why (not re-litigating, just recording):**
- Pipeline: Python, because `cdsapi` (the official, currently-recommended Copernicus
  client — NOT the newer `ecmwf-datastores-client`, which ECMWF itself says not to
  migrate to yet) is Python-only.
- DB: Postgres via Supabase — relational fits this data (one row per location per
  year) far better than a document store, and Supabase's auto-generated REST API
  (PostgREST) means the frontend can often read data directly without a hand-written
  backend at all.
- Compute: GitHub Actions scheduled workflow (`on: schedule`, daily) — no VM, no
  persistent server. This is genuinely enough for the workload (a few small point
  pulls once a day), not a corner cut.
- Frontend: static HTML + vanilla TS, regenerated by the same daily job. Not Next.js
  (overkill for a handful of screens with no per-request logic) and not a pure
  client-rendered SPA either — the deciding factor is that each city's page needs
  correct baked-in Open Graph meta tags for social share previews, which static
  generation gives for free and a client-only SPA doesn't.
- Map: Leaflet.js + OpenStreetMap tiles for the real product (the wireframe used an
  abstract grid only because that tool's sandbox blocks live map tiles — no such
  restriction here).

## 2. First Backend Steps — the Data Pipeline (detailed)

**Step 1 — Pick the dataset.**
Primary: `derived-era5-single-levels-daily-statistics`. This computes daily
min/max/mean 2m temperature server-side from ERA5's hourly data at request time —
exactly what the growing-degree-day model needs, no manual hourly aggregation.
Backup/fallback if finer granularity is ever needed: `reanalysis-era5-single-levels-timeseries`
(point-extraction, hourly, 1940–present).

Do **not** use ECA&D or E-OBS — both are explicitly restricted to non-commercial
research and education use. Copernicus's own CDS products (ERA5 included) are
openly licensed for any use, commercial included. This distinction was already
nearly a mistake once — worth a code comment or README line so it isn't repeated.

**Step 2 — Choose the initial location list.**
~15–30 points, not a full-Europe grid, for two reasons: API load stays small and
predictable, and the validation effort (§3) stays tractable. Bias the list toward
climate-zone diversity (at least one maritime, one continental, one Mediterranean,
one Nordic) rather than convenience — clustering all launch cities in one climate
zone undermines the point of validating across zones at all.

Architect this as **data, not code**: locations are rows in a table (name, lat, lon,
climate zone tag), not a hardcoded enum. Adding a city later — or, eventually, moving
toward broader grid coverage the way USA-NPN's model does under the hood — should be
"add a row," never a rewrite. See §5 for why this matters for the growth story.

**Step 3 — One-time historical pull.**
Daily min/max temperature, 1991–2020 (current WMO baseline period) per location, for
baseline computation. Pull back to ERA5's 1940 start for the same locations too —
needed for the multi-decade trend chart, and free to grab at the same time.

**Step 4 — Implement the phenology model.**
Adapt the Extended Spring Index (SI-x) growing-degree-day model. Don't write this
from scratch — port from `pyPhenology` (github.com/sdtaylor/pyPhenology) and/or
USA-NPN's own `gridded_models` repo (github.com/usa-npn/gridded_models), both
open source, both implementing the published formula.

Known refinement worth building in from day one, not retrofitting later: European
research found leaf-out is more sensitive to **daytime (max) temperature** than to
flat daily mean — weight the degree-day accumulation toward daily max rather than
mean from the start.

**Step 5 — Compute baseline, then current year.**
Run the model across the full historical pull per location → one modeled leaf-out
day-of-year per year → average 1991–2020 → that location's baseline. Then pull the
current year so far (ERA5 lags ~5 days) and run the same model for the live
"X days earlier/later" comparison.

**Step 6 — Store results.**
One row per (location, year): modeled day, delta vs. baseline. Small table, trivial
to query for both the per-city page and the map/table view.

**Step 7 — Automate the daily refresh.**
GitHub Actions, `on: schedule`, daily. Design for CDS's real behavior, not the happy
path — requests queue server-side and can occasionally take far longer than expected
(there's a literal ECMWF forum thread titled "CDS API queued indefinitely"). Give the
job a sane timeout and let a failed/timed-out run simply skip to tomorrow rather than
treating a slow queue as a fatal error — a day's delay on a number that changes over
weeks is a non-issue.

**Step 8 — Regenerate the static site as the last step of the same job**, so the
published pages and the underlying data are never out of sync.

## 3. Model Validation — detailed, because this is the credibility-critical part

**The honest baseline to design around:** published European studies evaluating this
class of model report calibration errors around **6.6–8.6 days RMSE** depending on
species. The app should present this as a range or an explicit "~within a week"
caveat on the methodology page — not a bare single-day number implying more
precision than the underlying science supports.

**How many validation points is "enough"?** There's no fixed correct number — but
there is a better framing than city count: statistical confidence comes from the
number of independent (location, year) comparisons, not the number of distinct
cities. Target roughly **5–8 validation sites spanning distinct climate zones**,
each checked against **15–20+ years of independent reference data** — on the order
of 75–150+ real comparisons, which is enough to compute an actual bias and spread
rather than a handful of anecdotes. Three cities all in one climate zone, however
many years deep, tells you nothing about whether the model transfers to a different
climate zone.

**Where to actually find reference data, in order of how easy each is:**
1. **DWD (Germany) open data** — opendata.dwd.de. Germany is the single
   best-covered region in Europe for this (confirmed visually via PEP725's public
   station map). DWD publishes its own phenology data under its own open terms
   (separate from PEP725's pooled non-commercial restriction), including ~1,200
   named stations and a ready-made 1km gridded annual phenology product that could
   double as a validation layer on its own.
2. **Nature's Calendar (Woodland Trust, UK)** — ~3 million records back to 1736,
   live maps, published seasonal reports. Check their specific data-access terms
   before relying on bulk figures from it.
3. **PEP725's public station map** (pep725.eu) — visual only, no login needed. Use
   it to see where good station density exists; the underlying observation data
   itself is licensed for research/education only, so don't bulk-download it —
   spot-checking a handful of already-published individual figures against it is a
   different, reasonable use.
4. **The plain public-knowledge fallback** — for cities without an easy scientific
   source, a well-known city's typical last-frost or bloom date is usually
   findable through ordinary horticultural/gardening sources. Good enough for a
   first plausibility pass, not a substitute for the scientific sources above where
   available.

**If validation shows a mismatch:**
- **Consistent offset** (e.g., always ~6 days early) → apply a calibration
  correction constant. Normal, expected, described in the literature — not a sign
  the approach is broken.
- **Inconsistent by region** → narrow the launch list to climate zones where it
  demonstrably works; don't launch uniformly just because the pipeline *can* compute
  a number for anywhere.
- **Not reliable anywhere** → drop the precise "X days" framing entirely in favor of
  a categorical badge ("earlier / typical / later than usual"). Still delivers the
  core value without overclaiming precision.

**Documenting the process — build this as a running log from day one, not a
retroactive writeup.** Keep `/docs/validation.md` (or a small DB table) with one row
per check: city, climate zone, model output, reference value, source, date checked.
This feeds two things at once: the public "Methodology" page (turning it from a
generic explainer into actual displayed evidence), and standalone content — "how we
checked our model before trusting it" is exactly the kind of science-communication
post that fits the marketing plan in §6.

## 4. The idea worth stealing from the US version (important — don't lose this)

USA-NPN's actual model is a **continuous 1km grid covering the entire continental
US** — it is not limited to any fixed city list. The "88% of 242 major cities saw
earlier spring" framing that gets picked up by NYT/Bloomberg/etc. every year is a
**curated public-reporting subset extracted from that grid purely for storytelling**
— the model itself never stopped working everywhere else.

Copy this exact pattern: architect the model/data layer to be capable of running for
any lat/lon (per §2's "locations are data, not code" note), but do the actual
**marketing and public storytelling around a curated, editorially-chosen subset of
cities** — the ones that are validated, interesting, or make a good ranking/story.
The technical coverage and the public-facing "supported cities" list don't have to be
the same list, and shouldn't be conflated. This is also the direct justification for
not over-engineering "works everywhere" before launch — USA-NPN didn't either.

## 5. Frontend (high level)

- Turn the existing wireframe screens into real static templates, generated by the
  pipeline's last step, deployed to Cloudflare Pages.
- Location search: geocode via an open geocoder (Nominatim/OSM); snap to nearest
  supported point; **say so explicitly** ("showing results for the nearest supported
  location, ~12km away") rather than silently substituting.
- Leaflet + OSM for the real map view; keep the accessible table view as an equal,
  first-class alternative (not a fallback), per the original wireframe intent.
- Vanilla TS for the interactive bits only (search, sortable table, map init) —
  reach for something like TanStack Query later only if this genuinely gets
  unwieldy, not preemptively.

## 6. Engagement & Notifications (high level)

- Design around push, not pull, given the real "check once and never again" risk
  identified early on: an email digest (Brevo, EU-based) is the primary channel.
- Treat push notifications as a later enhancement, not a launch dependency — iOS web
  push has real, EU-specific complications tied to Apple's DMA compliance changes
  that are worth re-verifying before depending on them.
- Multiple phenology events per year (leaf-out, bloom, first frost via §7's frost/
  growing-season add-ons, leaf-fall eventually) instead of one annual moment, so
  there's more than a single yearly touchpoint.

## 7. Marketing & Content (high level)

- Instagram from day one — the content is nearly free once the pipeline exists:
  per-city cards, cross-city rankings, the spring-stripes chart, frost-date content
  for a gardening audience, and "how we validated this" explainer content from §3's
  log.
- The "steal from the US" framing (§4) is itself good press-facing copy: "the first
  tool doing for Europe what NOAA/NYT-covered USA-NPN data does for the US."
- Growing-season-length and last-frost-date screens (already mocked up) extend reach
  into a gardening audience distinct from the climate-awareness audience, at near
  zero extra pipeline cost.
- **atproto/Bluesky publishing**, alongside Instagram, not instead of it: post the
  same daily/weekly cards (per-city results, cross-city rankings, validation-log
  entries from §3) to a Bluesky account via the API. Near-zero marginal cost once
  the image-generation step for Instagram exists — same assets, second channel.
  Fits the project's own "open, EU-native data" premise (§1) better than a
  closed platform does, and put the account on a **Eurosky** PDS (EU-hosted) rather
  than Bluesky's own, so the data-sovereignty story is consistent end to end.
  Optional stretch, not launch-blocking: mirror the longer validation-log writeups
  as posts on an atproto blogging service (e.g. WhiteWind) for a shareable
  permalink per entry, instead of only a section of a static methodology page.

## 8. Monetization (high level)

- Ko-fi tip button for v1 — no other monetization work needed until real usage
  data says otherwise.

## 9. Building-in-public Journey Log (high level)

- Keep a running, dated log of the build itself — not just the validation results
  from §3, but the whole process: model-tuning decisions, pipeline debugging,
  dead ends, "aha" moments, screenshots of the dashboard/charts as they evolve.
  This is the raw material for §7's Instagram/atproto content — a post is much
  easier to write from "here's what actually happened on 2026-09-27" than from
  memory weeks later.
- See `CLAUDE.md` for the concrete format and where entries live — the short
  version is one dated file per entry under `/journal/`, written as milestones
  happen (a validation run completes, a bug gets fixed, a chart first renders),
  not batched at the end.
- Screenshots matter as much as text for this content (dashboard states, chart
  outputs, terminal validation results) — captured alongside the entry they
  belong to, not as an afterthought.
